# Модель данных и MCP-инструменты — черновик для ТЗ

Черновик по решениям штурма. Задача 1 доводит его до `docs/spec.md`; спорные места помечены «?» и продублированы в `docs/questions.md`.

## Сущности

### Запись (record)

| Поле | Тип | Обязательно | Примечание |
|---|---|---|---|
| id | uuid | да | |
| type | `conclusion` \| `question` | да | вывод или открытый вопрос |
| kind | `fact` \| `rule` \| `hypothesis` | для вывода | факт / правило бюро / гипотеза |
| text | строка ≤ 300 знаков | да | формулировка; длиннее — это документ, ему место в справке, здесь — ссылка |
| core | ссылка на ядро | да | Проектирование · BIM и Revit · Процессы бюро · Инструменты |
| project | внешний id объекта из Schema Teams | нет | область «проект»; без проекта — область «бюро» |
| software_version | строка | нет | Revit 2026, версия плагина, редакция нормы — от чего зависит вывод |
| not_applicable | строка | нет | когда вывод не применим |
| source | строка | да | откуда: сессия агента (дата, задача), реестр проверок, форма |
| author | ссылка на актора | да | |
| confirmed_by_author | bool | да | первый шаг двойного контроля; сервис не может его проверить — только инструкция агенту |
| status | см. состояния | да | |
| requests_count | int | да | сколько раз запись отдавалась агентам (для приоритета модерации) |
| worked (n) | int | да | число «сработало» от разных акторов |
| failed (b) | int | да | число «не сработало» |
| needs_check | bool | да | пометка «проверить» после смены версии ПО |
| created, updated | datetime | да | |

Показатель доверия: `score = n / (n + b + 1)`. При `score ≤ 0.25` вывод считается ложным и не выдаётся по умолчанию. **?** При `n = b = 0` формула даёт 0 — свежая запись окажется «ложной». Предложение: порог применять только при `n + b ≥ 1` (или ≥ 2); до этого показывать «нет отметок». Решает руководитель.

Состояния записи: `draft` (черновик у агента, в базу не попадает) → `pending` (в очереди модерации) → `accepted` | `rejected` | `disputed` (есть противоречие, ждёт модератора). `accepted` + `needs_check` — выдаётся с пометкой.

Для `type = question`: kind не нужен; состояние `open` → `answered` (есть связь `answers` от вывода) → `closed`.

### Связь (link)

| Поле | Значения |
|---|---|
| from, to | id записей (или ядро / проект / внешний документ для некоторых типов) |
| type | `contradicts` (противоречит; только между фактами и гипотезами — для правил бюро запрещено, см. решение 7) · `answers` (вывод отвечает на вопрос) · `derived_from` (вывод выведен из другого) · `reflected_in` (отражён в стандарте / справке — внешняя ссылка) · `source_registry` (из реестра проверок) |
| created_by | актор |
| created | datetime |

Принадлежность к ядру и проекту — поля записи, не связи (так проще для запросов «что мы знаем о ядре X / проекте Y»). **?** Если выбрана графовая СУБД — то же самое можно выразить рёбрами; решить в ADR.

### Ядро (core)

`id`, `name`, `description`. Список фиксированный, правится модератором. Добавления предлагает Claude при периодическом разборе.

### Проект (project)

`external_id` из Schema Teams, `name`, `active`. Синхронизация по API Schema Teams (есть MCP-инструмент списка объектов).

### Актор (actor)

Сотрудник или агент. `id`, `display` (обезличенный ярлык, например «проектировщик АР-2» — настоящие имена живут только на сервере бюро, в репозитории их нет), `kind` (`human` | `claude` | `chatgpt` | `local`), `token` (хэш), `scopes` (`read`, `propose`, `feedback`, `moderate`), `projects` (доступ к области «проект»). У каждого сотрудника и у каждого его агента — свой токен; токен ChatGPT может быть только на чтение.

### Отметка (feedback)

`record_id`, `actor_id`, `worked` (bool), `comment`, `created`. Один актор — одна отметка на запись (повторная заменяет). Пересчёт n и b — по уникальным **людям** за актором, не по агентам (**?** уточнить: считать ли два агента одного человека за одного).

### Очередь модерации

Представление, не таблица: все `pending` и `disputed`, порядок — `disputed` → `requests_count > 0` по убыванию → остальные по дате.

### Датасет

Выгрузка JSONL: записи со всеми полями и историей статусов, отметки, вопросы, решения модератора (принял / отклонил / объединил). Без имён людей — ярлыки акторов. Команда `export` в CLI сервиса.

## MCP-инструменты — черновик

Имена и состав — к обсуждению в задаче 1. Все ответы агенту — короткие, с показателем доверия и пометками, чтобы не раздувать контекст.

| Инструмент | Вход | Выход | Кому |
|---|---|---|---|
| `brain_search` | запрос (текст), ядро?, проект?, лимит (по умолчанию 5) | записи: текст, вид, показатель (`75 % · 3 за, 0 против`), `needs_check`, противоречащие записи рядом | все с `read` |
| `brain_get` | id | запись целиком со связями | `read` |
| `brain_propose` | запись по формату выше, `confirmed_by_author = true` | id, состояние `pending` | `propose` |
| `brain_ask` | текст вопроса, ядро, проект? | id вопроса; если похожий вопрос уже есть — его id | `propose` |
| `brain_feedback` | id, `worked`, комментарий? | новый показатель | `feedback` |
| `brain_cores` | — | список ядер | `read` |
| `brain_projects` | — | активные проекты из Schema Teams | `read` |
| `brain_moderate` | id, решение (`accept` \| `reject` \| `merge_into`), комментарий | состояние | `moderate` |
| `brain_queue` | лимит | очередь модерации с приоритетом | `moderate` |

Каждый вызов `brain_search` / `brain_get` увеличивает `requests_count` у выданных записей.

Инструкция агенту (живёт в навыке, не в сервисе): показать автору черновик записи и отправлять `brain_propose` только после явного «ок»; в конце задачи, если применял записи из базы, — один вопрос «сработало?» и `brain_feedback`.

## Формат md-записи для шага 0 (до сервера)

Навык «Выводы» пишет по одному файлу на запись в папку выводов пользователя: `ГГГГ-ММ-ДД — <кратко>.md`. Импорт в сервис — механический, поэтому поля те же, что у записи.

```markdown
---
type: вывод            # вывод | вопрос
kind: факт             # факт | правило | гипотеза — только для вывода
core: BIM и Revit      # Проектирование | BIM и Revit | Процессы бюро | Инструменты
project:               # код объекта из Schema Teams, если есть
software_version: Revit 2026
not_applicable: для связанных файлов с общими уровнями
source: сессия 2026-10-15, задача «планы этажей, оси»
confirmed_by_author: true
created: 2026-10-15
---
При копировании листов с планами оси обрезаются, если у видов разные «зоны обрезки»; перед копированием выровнять зоны обрезки по шаблонному виду.
```

Правила: текст — одна-три фразы, до 300 знаков; без имён людей и путей; `project` — код объекта, не адрес. Значения перечислений — по-русски, как в примере; сервис при импорте сопоставляет их с внутренними кодами.
