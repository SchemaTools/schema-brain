# Schema Brain — ТЗ первой версии

Версия ТЗ: 0.1 (2026-10-15), задача 1. Основа — `docs/data-model.md` и решения из `docs/decisions.md`; стек — `docs/adr/001-стек-и-хранение.md`.

Пометка **[РВ n]** — рабочий вариант до ответа руководителя на вопрос n из `docs/questions.md`. Работа по нему идёт, ответ может его поменять.

## 2. Люди, агенты, доступ

### 2.1. Сотрудник и токены

Сотрудник (`person`) — человек бюро. В репозитории и в датасете — только обезличенный ярлык («проектировщик АР-2»); как ярлык соотносится с человеком, знает только модератор, на сервере.

У сотрудника несколько **токенов** — по одному на каждого его агента и один для веба. Токен знает, чей он и какой у него клиент: `web`, `claude`, `chatgpt`, `codex`, `local`.

Так снимается вопрос «актор — человек или агент»: **автор и отметки привязаны к сотруднику**, а клиент записывается рядом для датасета. Две отметки от Claude и ChatGPT одного человека — одна отметка **[РВ 2]**.

Токен: приставка `sbt_` и 43 знака (32 случайных байта, base64url). В базе — только хэш SHA-256 и первые 8 знаков для узнавания в списке. Показывается один раз при выпуске. Отзыв — сразу.

### 2.2. Права

| Право | Что даёт |
|---|---|
| `read` | поиск, чтение записей, ядер, проектов |
| `propose` | отправить запись или вопрос |
| `feedback` | отметка «сработало / не сработало» |
| `moderate` | очередь, решения модератора, правка записей и связей, сотрудники и токены, настройки |

По умолчанию у токена агента — `read`, `propose`, `feedback`; у веб-токена модератора — все четыре. Токен можно выпустить только на чтение (например, для ChatGPT).

### 2.3. Области

Две области: **бюро** (у записи нет проекта) и **проект** (есть). Личной области нет.

В первой версии все сотрудники видят записи всех проектов: в бюро 6–20 человек, а записи проектов — то, что сотрудник сам решил передать коллегам **[РВ 9]**. Проект служит фильтром и контекстом поиска.

### 2.4. Вход в веб

По личному веб-токену: сотрудник вставляет его один раз, сервис ставит cookie сеанса (httpOnly, 30 дней). Паролей в сервисе нет. Токен выдаёт модератор.

### 3.2. Связь (`link`)

| Поле | Значение |
|---|---|
| `from_id`, `to_id` | записи |
| `type` | см. ниже |
| `created_by`, `created` | кто и когда |

| Тип | Смысл | Ограничение |
|---|---|---|
| `contradicts` | противоречит | только между фактами и гипотезами (решение 7); хранится одной строкой, читается в обе стороны |
| `answers` | вывод отвечает на вопрос | `from` — вывод, `to` — вопрос |
| `derived_from` | выведен из другой записи | |
| `replaces` | правило заменило прежнее | только между правилами; прежнее — в состоянии `replaced` |
| `merged_into` | объединена с другой записью | ставит модератор при решении «объединить» |

Внешние ссылки (страница справки, реестр проверок) — не связи между записями, а поле `refs` записи: список `{вид, адрес, подпись}`. Вид — `wiki` (страница справки Schema Teams) или `registry` (реестр проверок). Адреса — внутренние адреса бюро, в репозиторий не попадают.

### 3.3. Ядро (`core`)

`id`, `code`, `name`, `description`, `sort`. На старте четыре:

| code | Название |
|---|---|
| `design` | Проектирование |
| `bim` | BIM и Revit |
| `process` | Процессы бюро |
| `tools` | Инструменты (плагины, навыки, MCP) |

Список правит модератор в веб-настройках. Удалить ядро с записями нельзя — только переименовать или перенести записи.

### 3.4. Проект (`project`)

`id`, `external_id` (id объекта в Schema Teams), `code` (код объекта, например вида «NN/ГГГГ-NN»), `name`, `active`. Синхронизация — раздел 9.2.

### 3.5. Отметка (`feedback`)

`record_id`, `person_id`, `client`, `worked` (да/нет), `comment` (до 300), `software_version` (необязательно — на какой версии проверено), `created`. Один сотрудник — одна действующая отметка на запись; новая заменяет прежнюю, прежняя остаётся в истории.

### 3.6. Журнал записи (`record_event`)

Каждое изменение записи пишется в журнал в той же транзакции: создание, правка (было → стало), смена состояния, решение модератора с комментарием, отметка, связь, запрос агентом не пишется (только счётчик). Из журнала строятся карточка в вебе и датасет.

### 3.7. Текущие версии (`software_current`)

`product` (Revit, Schema.Tools, …), `version`, `changed`. Правит модератор. Нужно для пометки «проверить» (раздел 5.4).

### 3.8. Перечисления по-русски

В md-файлах, вебе и ответах агентам — русские названия; в базе и API — коды.

| Код | По-русски |
|---|---|
| `conclusion` / `question` | вывод / вопрос |
| `fact` / `rule` / `hypothesis` | факт / правило / гипотеза |
| `pending` | на модерации |
| `disputed` | противоречие, на модерации |
| `accepted` | принята |
| `rejected` | отклонена |
| `merged` | объединена |
| `replaced` | заменена |
| `open` / `answered` / `closed` | открыт / есть ответ / закрыт |

## 4. Состояния

### 4.1. Вывод

```
(черновик у агента — в сервис не попадает)
        │ автор сказал «ок» → brain_propose
        ▼
     pending ──есть противоречие──► disputed
        │                              │
        └──────── модератор ───────────┘
          │        │        │         │
      accepted  rejected  merged   accepted + replaces
          │                          (прежнее правило → replaced)
          └── пометка needs_check при смене версии (запись остаётся accepted)
```

- Агентам по умолчанию выдаются только `accepted`. `pending` и `disputed` видит модератор и сам автор.
- `accepted` с `needs_check` выдаётся с пометкой «проверить: …».
- `accepted` с показателем доверия не выше 25 % — «ложная» (раздел 5.3): агентам не выдаётся, в вебе — отдельный фильтр «ложные».
- Модератор может вернуть `rejected` в `pending`; остальные состояния окончательные (их можно только заменить новой записью).

### 4.2. Вопрос

`open` → `answered` (принят вывод со связью `answers` на вопрос) → `closed` (модератор закрыл). Модератор может закрыть вопрос без ответа или отклонить (`rejected` — например, вопрос с личными данными).

Вопросы **не проходят модерацию до публикации** **[РВ 10]**: вопрос ничего не утверждает, а отвечать на него — руководителю. Автор подтверждает вопрос так же, как вывод.

## 5. Правила

### 5.1. Двойной контроль

1. Агент показывает автору черновик и отправляет запись только после явного «ок». Это инструкция навыка: сервис проверить её не может, но **отклоняет запись без `confirmed_by_author = true`**.
2. Модератор принимает, отклоняет, объединяет или заменяет. Может поправить текст и поля до принятия; правка — в журнале.

Порога подтверждений для области «бюро» нет: после модерации запись видна всем.

### 5.2. Отметки и пересчёт n и b

- n — число сотрудников, чья действующая отметка «сработало»; b — «не сработало».
- Агенты одного сотрудника считаются как один человек **[РВ 2]**.
- Отметка самого автора хранится, но в n и b не входит: «подтверждение делом» — от коллег **[РВ 2]**.
- Отметки принимаются только у записей `accepted`.
- n и b пересчитываются в той же транзакции, что и отметка.

### 5.3. Показатель доверия

`score = n / (n + b + 1)`.

| Отметок (n + b) | Показ | Выдача агентам |
|---|---|---|
| 0 | «нет отметок» | да |
| ≥ 1, score > 25 % | «75 % · 3 за, 0 против» | да |
| ≥ 1, score ≤ 25 % | «ложная · 0 за, 2 против» | нет (только по прямому запросу `brain_get` или с флагом «показать ложные») |

Порог применяется при `n + b ≥ 1` **[РВ 1]**. Следствие: одна отметка «не сработало» у свежей записи сразу делает её ложной (0 / 2 = 0 %). Если это слишком строго — порог можно применять с `n + b ≥ 2`; одна строка настройки.

Формула и порог — в одном модуле с тестами, порог и минимум отметок — настройки.

### 5.4. Срок годности по версии

1. Сервис выделяет продукт из `software_version`: всё до номера версии («Revit 2026» → «Revit»).
2. Когда модератор меняет текущую версию продукта (раздел 3.7), всем принятым записям этого продукта с другой версией ставится `needs_check`. Показатель не сбрасывается.
3. Пометка снимается, когда приходит отметка «сработало» с текущей версией (агент передаёт версию, на которой проверял), или вручную модератором **[РВ 11]**.

### 5.5. Противоречия и дубли

При отправке записи сервис ищет до трёх похожих принятых записей (тот же поиск, что раздел 6) и возвращает их агенту вместе с номером новой записи.

- Агент по инструкции навыка сравнивает и, если новая запись противоречит найденной, передаёт `contradicts: [№]` — запись встаёт в `disputed`.
- Если новая запись повторяет найденную, агент предлагает автору поставить отметку «сработало» существующей вместо новой записи.
- Модератор может добавить или снять `contradicts` вручную.

Правила проверки:

- `contradicts` — только между фактами и гипотезами. Если новая запись противоречит **правилу бюро**, она всё равно встаёт в `disputed`, но принять её модератор может только решением «заменить» (старое правило → `replaced`) или «отклонить». У правила — один ответ (решение 7).
- Принятые факты и гипотезы-соперники выдаются агенту рядом: «противоречит № 130 (60 %)».

### 5.6. Очередь модерации

Не таблица, а выборка `pending` и `disputed`, порядок:

1. `disputed` — по дате, старые выше;
2. `pending` с `requests_count > 0` — по убыванию счётчика;
3. остальные `pending` — по дате, старые выше.

Счётчик запросов:

- у принятой записи растёт при каждой выдаче агенту (`brain_search` — только записи, попавшие в ответ; `brain_get`);
- запись на модерации агенту не выдаётся, но если она попала бы в ответ `brain_search`, её счётчик тоже растёт — так в очереди выше оказывается то, что агентам уже нужно.

Отдельно у вопросов — счётчик «спросили ещё раз» (раздел 7, `brain_ask`); открытые вопросы в вебе сортируются по нему.

Расчёт порядка — чистая функция с тестами.

## 6. Поиск

1. Запрос → полнотекстовый поиск PostgreSQL (`russian`, слова с префиксом, как в базе знаний объекта Schema Teams).
2. Когда подключена модель векторов — ещё поиск по близости векторов; результаты двух поисков сливаются (взаимный ранг, RRF).
3. Фильтры: ядро, проект (записи проекта **и** бюро), тип, вид, состояние (по умолчанию — принятые, не ложные).
4. К каждой найденной записи — противоречащие ей (связь `contradicts`) и ответы, если это вопрос.
5. Лимит по умолчанию — 5, наибольший — 20.

Латинские буквы, похожие на русские, перед цифрой («B25», «A500») приводятся к русским и в тексте, и в запросе — как в Schema Teams.

## 7. MCP-инструменты

Ответы агенту — короткие строки, чтобы не раздувать контекст. Пример ответа `brain_search`:

```
№ 128 · правило · BIM и Revit · 75 % (3 за, 0 против)
При копировании листов с планами оси обрезаются, если у видов разные зоны обрезки; перед копированием выровнять зоны по шаблонному виду.
Не применимо: для связанных файлов с общими уровнями.
Проверить: записано для Revit 2026, текущая — Revit 2027.
```

| Инструмент | Вход | Выход | Право |
|---|---|---|---|
| `brain_search` | `query`, `core?`, `project?`, `type?` (по умолчанию выводы), `limit?` | записи в формате выше; соперники рядом | `read` |
| `brain_get` | `number` | запись целиком: поля, показатель, связи, внешние ссылки | `read` |
| `brain_propose` | `type`, `kind`, `text`, `core`, `project?`, `software_version?`, `not_applicable?`, `source`, `confirmed_by_author`, `contradicts?`, `derived_from?`, `answers?` | номер, состояние; до трёх похожих записей | `propose` |
| `brain_ask` | `text`, `core`, `project?`, `source`, `confirmed_by_author` | номер вопроса; если похожий открытый вопрос уже есть — его номер, и у него растёт счётчик «спросили ещё раз» | `propose` |
| `brain_feedback` | `number`, `worked`, `comment?`, `software_version?` | новый показатель | `feedback` |
| `brain_cores` | — | ядра | `read` |
| `brain_projects` | `query?` | активные проекты: код и название | `read` |
| `brain_queue` | `limit?` | очередь модерации в порядке раздела 5.6 | `moderate` |
| `brain_moderate` | `number`, `decision` (`accept` \| `reject` \| `merge` \| `replace`), `target?` (для объединения и замены), `edits?` (поправки полей), `comment?` | новое состояние | `moderate` |

`core` и `kind` принимаются и кодом, и по-русски («BIM и Revit», «правило»). `project` — код объекта.

Инструкции агенту (живут в навыке «Выводы», не в сервисе):

- искать в базе по ходу задачи, не только в начале (решение 9);
- показать автору черновик, отправлять только после «ок»;
- сравнить с похожими записями из ответа `brain_propose`: противоречие → `contradicts`, повтор → предложить отметку вместо записи;
- в конце задачи, если применял записи, — один вопрос «сработало?» и `brain_feedback`;
- не больше трёх записей за сессию.

## 8. HTTP API

Все маршруты — под `/api`, токен — в заголовке `Authorization: Bearer sbt_…` или cookie сеанса веба. Ответы — JSON; ошибки — `{ "error": "<код>", "message": "<по-русски>" }`.

| Маршрут | Что |
|---|---|
| `GET /api/health` | состояние сервиса и базы, версия; без токена |
| `GET /api/records` | список с фильтрами `q`, `core`, `project`, `type`, `kind`, `status`, `false`, `needs_check`; постранично |
| `GET /api/records/:number` | запись целиком со связями и журналом |
| `POST /api/records` | отправить запись или вопрос |
| `PATCH /api/records/:number` | правка модератором; версия записи в теле, чужая версия — 409 |
| `POST /api/records/:number/feedback` | отметка |
| `POST /api/records/:number/moderate` | решение модератора |
| `POST /api/links`, `DELETE /api/links/:id` | связи (модератор; автор — при отправке записи) |
| `GET /api/queue` | очередь модерации |
| `GET /api/graph?center=&depth=` | узлы и рёбра для графа (глубина до 3) |
| `GET /api/cores`, `PUT /api/cores/:code` | ядра |
| `GET /api/projects` | проекты |
| `GET/PUT /api/software` | текущие версии |
| `GET/POST /api/persons`, `POST /api/persons/:id/tokens`, `DELETE /api/tokens/:id` | сотрудники и токены (модератор) |
| `POST /api/session`, `DELETE /api/session` | вход и выход в вебе |

MCP-пакет — тонкая обёртка над этими маршрутами.

## 9. Импорт и связь с другими системами

### 9.1. Импорт md-записей шага 0

Команда `brain import-md <папка> --person <ярлык>` (в контейнере сервиса):

1. Читает файлы `*.md` с заголовком в формате `docs/data-model.md`.
2. Проверяет поля и длину текста, сопоставляет русские значения с кодами (раздел 3.8); ядро — по названию, проект — по коду.
3. Пропускает файлы, уже импортированные (по хэшу текста и автору) — повторный запуск безопасен.
4. Создаёт записи в `pending` (или вопросы в `open`) с источником «импорт md: <имя файла>».
5. Печатает отчёт: принято, пропущено (повтор), ошибки с причиной по каждому файлу.

Чей файл — задаёт `--person`: откуда брать папки, зависит от ответа на вопрос 6 **[РВ 6]** — рабочий вариант: у каждого сотрудника своя папка, импорт — по одной.

Разбор заголовка и проверка — чистые функции с тестами; те же функции использует навык для проверки формата (через общий пакет).

### 9.2. Проекты из Schema Teams

Сервис раз в час и по кнопке читает список объектов из API Schema Teams (адрес и токен только на чтение — в настройках сервера, `.env`). Новые объекты добавляются, удалённые и закрытые помечаются `active = false`; записи по ним остаются. Если Schema Teams не настроен, проекты добавляет модератор вручную.

### 9.3. Справка Schema Teams

Команда `brain export-wiki --core <код>` собирает страницу в Markdown: принятые правила и факты ядра с показателем выше порога, сгруппированные по видам, с номерами записей. Опубликовать страницу руководитель просит Claude через MCP Schema Teams (`st_wiki_save` — с предпросмотром и подтверждением). Прямой записи из сервиса в справку в первой версии нет: меньше токенов с правом записи и видно, что публикуется **[РВ 12]**.

### 9.4. Реестры проверок

`tools/registry-scan` (задача 3) выдаёт кандидатов «типовая ошибка» в md в формате шага 0 (`source: реестр проверок`, `kind: факт`, в `refs` — реестр); дальше — тот же импорт md, записи идут на модерацию.

## 10. Выгрузки

### 10.1. Датасет для дообучения

Команда `brain export-dataset <папка>` — пять файлов JSONL:

| Файл | Строка |
|---|---|
| `records.jsonl` | запись со всеми полями (без вектора), ярлык автора и клиент |
| `links.jsonl` | связь |
| `feedback.jsonl` | отметка, включая заменённые |
| `events.jsonl` | событие журнала: правки (было → стало), решения модератора с комментариями |
| `meta.json` | версия формата, версия сервиса, дата выгрузки, число строк |

Вместо людей — ярлыки. Токенов, хэшей и cookie в выгрузке нет.

### 10.2. Экспорт в md в стиле Obsidian — этап 5

Одна запись — один файл, связи — ссылки `[[№ 128]]`, ядро и проект — в заголовке.

## 12. Установка и эксплуатация

- `docker compose up`: контейнеры `db` (`pgvector/pgvector:pg16`) и `app`; модель векторов — третьим контейнером, если её утвердят **[РВ 7]**. Порт базы наружу не открывается.
- Настройки — в `deploy/.env` (в репозиторий не попадает); в репозитории — `deploy/.env.example` с пустыми значениями.
- Миграции — при старте сервиса. Резервная копия — `pg_dump` по расписанию в том `backups`.
- Установка и обновление — по SSH из локальной сети; инструкция без адресов и имён.
- Журнал сервера — с ротацией. Каждый запрос с токеном пишется с ярлыком сотрудника и клиентом, без текста записей.
- Ограничения: тело запроса — до 64 КБ; поиск — до 20 записей; не больше 30 отправок в час с одного токена (защита от зацикленного агента).

## 13. Проверки и тесты

- `npm run check` — типы, линтер, форматирование, тесты, лицензии зависимостей.
- Обязательно с тестами до Docker: показатель доверия и порог, пересчёт n и b по людям, порядок очереди, выделение продукта из версии и пометка «проверить», разбор md-записи, сопоставление русских значений, приведение латиницы к кириллице в поиске.
- Тесты с базой (поиск, транзакции, миграции) — на базе в Docker.
- `scripts/check-private-data.sh` — перед каждым пушем и в CI: адреса, почта, токены (`stt_`, `sbt_`), закрытые ключи, слова из `private/denylist.txt`.
- Каждый этап проверяется на реальных данных пилота (деперсонализированные копии вне репозитория); итоги — `docs/dev-notes/`.
