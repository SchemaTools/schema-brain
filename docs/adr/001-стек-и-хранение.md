# ADR 001 — стек и хранение

Статус: **утверждено** руководителем 2026-10-15 (предложено в тот же день).

## Коротко

Рекомендация: **PostgreSQL 16 с расширением pgvector**, а не графовая СУБД. Код сервиса — **на том же стеке, что Schema Teams**: TypeScript, Node.js 22, Fastify, Prisma, React + Vite, тесты на Vitest. MCP — небольшой пакет без зависимостей, как инструмент MCP Schema Teams.

Что это значит для бюро:

- на сервере два контейнера — база и сервис, как у Schema Teams; резервная копия — одна команда `pg_dump`;
- связи между записями хранятся в той же базе; граф в вебе рисуется из них, отдельная графовая база не нужна;
- поиск работает с первого дня (полнотекстовый, с русской морфологией, как в базе знаний объекта Schema Teams); смысл в первой версии понимает Claude — агент при поиске и при разборе базы; векторы — потом, на локальной модели бюро;
- один язык и одни приёмы в обоих сервисах: проще поддерживать, можно переносить готовые куски (токены, журнал, проверку на реальные данные, MCP-пакет).

## Что выбирали

Нужно хранить тысячи коротких записей (до 300 знаков) от 6–20 человек, связи между ними, отметки «сработало / не сработало», историю модерации. Нужны: поиск по смыслу, переход по связям, граф для человека, выгрузка в md и в датасет, запуск в Docker на одном сервере.

### Вариант А — PostgreSQL + pgvector

Записи — таблица, связи — отдельная таблица «откуда — куда — тип». Векторы — столбец `vector` у записи (расширение pgvector), индекс HNSW.

### Вариант Б — графовая СУБД (Neo4j, Memgraph и подобные)

Записи — узлы, связи — рёбра; запросы на языке Cypher. У Neo4j 5 есть векторный индекс.

## Сравнение по критериям из задачи 1

| Критерий | А: PostgreSQL + pgvector | Б: графовая СУБД |
|---|---|---|
| **Граф связей для человека** | Граф рисует веб (библиотека отрисовки графа в браузере) по данным из таблицы связей. На тысячах записей это мгновенно. Обход «на 2–3 шага от записи» — рекурсивный запрос SQL. | Обход связей — сильная сторона, есть встроенный просмотрщик. Но просмотрщик — инструмент разработчика, не экран для сотрудников бюро: веб с графом всё равно делать самим. |
| **Поиск по смыслу** | pgvector — зрелое расширение, индекс HNSW; поиск по смыслу и по словам (полнотекстовый, русская морфология) — в одном запросе вместе с фильтрами по ядру, проекту, статусу. | Векторный индекс есть у Neo4j 5; полнотекстовый поиск с русской морфологией слабее. Фильтры и поиск в одном запросе — возможно, но менее отработано. |
| **Простота в Docker на одном сервере** | Один контейнер `pgvector/pgvector:pg16` — та же PostgreSQL, что у Schema Teams, плюс расширение. Резервная копия и восстановление — уже отработанный приём. | Отдельная база на Java: требует памяти (от 1–2 ГБ), свои резервные копии, свой мониторинг. Вторая СУБД на сервере бюро — вдвое больше того, что надо знать и чинить. |
| **Объём: 6–20 человек, тысячи записей** | Многократный запас: PostgreSQL рассчитана на миллионы строк. | Тоже с запасом, но мощность графовой базы здесь не нужна: обходы на 2–3 шага по тысячам узлов SQL делает за миллисекунды. |
| **Экспорт в md (как в Obsidian) и датасет JSONL** | Обычный запрос → файлы. Связи → ссылки `[[…]]`. | То же самое, сложность одинаковая. |
| **Зрелость инструментов** | Prisma (уже в Schema Teams), драйверы, миграции, резервные копии — проверены на сервере бюро. Тип `vector` Prisma не знает: поиск — одним сырым запросом SQL, как поиск в базе знаний объекта Schema Teams. | Драйверы есть, но миграции схемы, тесты и резервные копии придётся выстраивать заново. Лицензии: Neo4j Community — GPLv3 и ограничения на кластер; у других вариантов свои условия. |
| **Модерация, токены, журнал, отметки** | Обычные таблицы с транзакциями — то, в чём реляционная база сильнее всего. | Возможно, но неестественно: учёт и транзакции — не профиль графовой базы. |

**Вывод.** Граф в Schema Brain — это способ смотреть на записи и переходить по связям, а не объём, для которого нужна специальная база. Всё, что даёт графовая СУБД, вариант А покрывает таблицей связей и рекурсивным запросом. Цена варианта Б — вторая СУБД на сервере и всё, что под неё придётся выстраивать с нуля.

**Когда пересмотреть.** Если записей станет сотни тысяч и понадобятся обходы на 5+ шагов с весами — вынести граф в отдельную базу можно позже: таблица связей переносится один к одному.

## Как устроен граф

1. **Хранение.** Записи — узлы; связи — таблица «откуда — куда — тип» (`docs/spec.md`, раздел 3.2). Ядра и проекты — поля записи, на графе показываются узлами.
2. **Обход.** «Всё, что связано с записью, на 2–3 шага» — один рекурсивный запрос SQL; API отдаёт вебу узлы и рёбра (`GET /api/graph?center=&depth=`).
3. **Для человека.** Экран «Граф» в вебе на Cytoscape.js: цвет узла — вид записи, размер — число запросов агентов, выделены «ложные» и «проверить»; противоречия — красный пунктир, «отвечает» и «выведен из» — свои линии; фильтры по ядру, проекту, состоянию; щелчок — карточка записи.
4. **Для агента.** Граф — в ответах: рядом с записью — противоречащие ей, у вопроса — ответы, `brain_get` — все связи записи.
5. **Obsidian (этап 5).** Связи выгружаются ссылками `[[№ …]]` — граф в Obsidian строится сам.
6. **Запас.** Если понадобятся глубокие обходы, поиск путей или графовые запросы — расширение Apache AGE (язык Cypher внутри той же PostgreSQL): без второй базы и без переноса данных.

Таблица связей и запрос обхода — в основе сервиса (задача 4); экран графа — этап 4, параллельно с пилотом.

| Часть | Выбор | Почему |
|---|---|---|
| База | PostgreSQL 16 + pgvector, образ `pgvector/pgvector:pg16` | см. выше; та же версия, что у Schema Teams |
| Сервер (API) | TypeScript, Node.js 22, Fastify, Zod | как в Schema Teams |
| Доступ к базе | Prisma; поиск — сырым SQL | как в Schema Teams; тип `vector` Prisma не поддерживает |

| Тесты | встроенный в Node.js `node --test`; с базой — на временной PostgreSQL (`embedded-postgres`, как в Schema Teams) | векторов в первой версии нет (решение 2026-10-15), pgvector для тестов не нужен; Vitest не понадобился — TypeScript запускается без сборки (уточнено при задаче 4б) |

## Поиск по смыслу: где считать векторы

Вектор (эмбеддинг) — числовой «отпечаток смысла» записи; его считает отдельная модель. Решение руководителя 2026-10-15: **пока без векторов, смысл — через Claude при разборе, потом — локальная модель бюро.** Тексты записей не покидают локальную сеть.

1. **Первая версия ищет полнотекстово** — PostgreSQL с русской морфологией, как база знаний объекта Schema Teams. Без внешних сервисов и новых зависимостей.
2. **Агент ищет несколькими формулировками** — синонимами и терминами, как их пишут по-разному («зона обрезки | crop region»); так он заменяет поиск по смыслу (`docs/spec.md`, раздел 6).
3. **Дубли и противоречия «разными словами» находит Claude при разборе** — модератор просит разобрать ядро, Claude сравнивает записи по смыслу и предлагает объединения и связи (`docs/spec.md`, раздел 6.1).
4. **Потом — векторы на локальной модели бюро**: столбец `vector` добавляется миграцией (pgvector уже в образе базы), записи и API не меняются.

## Подключение агентов

- **Claude на компьютере, Claude Code, Codex** — MCP-пакет на компьютере сотрудника ходит в API сервиса по локальной сети. Внешний адрес не нужен.
- **ChatGPT (веб и приложение)** подключает MCP-серверы со своих серверов, из интернета. Сервер в локальной сети бюро ему недоступен без выхода наружу. Решение руководителя 2026-10-15: ChatGPT в первой версии работает через Codex.

## Последствия

- Устройство сервера — как у Schema Teams: два контейнера (база, сервис).
- Резервное копирование, обновление по SSH, журнал — те же приёмы, что у Schema Teams.
- Проверка на реальные данные перед пушем — скрипт `scripts/check-private-data.sh` по образцу Schema Teams, включён в этот PR.
