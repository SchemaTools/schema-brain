# Schema Brain — вводные для Claude Code

Прочитать целиком перед первой задачей. Затем — `docs/decisions.md`, `docs/plan.md`, `docs/data-model.md`, `docs/questions.md`.

## Что это

Schema Brain — сервис архитектурного бюро Schema (6–20 человек), через который ИИ-агенты сотрудников (Claude, ChatGPT / Codex, позже — локальные модели) обмениваются знаниями: выводами из работы, открытыми вопросами, типовыми ошибками. Сервис работает в Docker на сервере бюро, в локальной сети; подключение агентов — через MCP. Для человека — просмотр записей и графа связей, модерация.

Главный принцип: помочь агентам быстрее прийти от задачи к нужному результату. Всё, что этому не служит, — не в первую версию.

Три сценария, нужны все: общая память о бюро («как у нас принято»); передача контекста по проектам между сотрудниками с разными ИИ; накопление опыта (замечания проверок, типовые ошибки, удачные решения).

## Роли

- **Руководитель** — ставит задачи, принимает работу, на старте — единственный модератор базы. Не программирует: общаться по-русски, по существу, объяснять технические развилки через последствия для бюро, а не через термины.
- **Claude Code** — пишет код, тесты, документацию; ведёт `docs/`.
- **Сотрудники бюро** — авторы записей через своих агентов. Пилот навыка — 5–6 человек на 3–5 дней; пилот сервиса — 5–7 человек на 2 недели.

## Решения — не пересматривать без руководителя

Полный список с датами — `docs/decisions.md`. Главное:

1. Модель данных — граф: типизированные записи и связи; поиск — по смыслу (векторный) плюс переход по связям.
2. Хранение — база, не файлы. Выгрузка в md со ссылками (как в Obsidian) — отдельный этап.
3. Данные попадают в сервис только по явному действию сотрудника. Личные чаты агентов в сервис не попадают. Личной области нет: области доступа — **проект** и **бюро**.
4. Двойной контроль: автор подтверждает запись в своём агенте → модератор подтверждает на сервисе. У записи есть поле «подтверждено автором». Порога подтверждений для области «бюро» нет: после модерации запись видна всем.
5. Запись — типизированная: текст до 300 знаков; вид — факт / правило бюро / гипотеза; ядро; проект (если есть); версия ПО или нормы, от которой зависит; «когда не применимо». Второй тип записи — **открытый вопрос** (агент не нашёл ответа в базе).
6. Показатель доверия `n / (n + b + 1)`: n — число «сработало», b — «не сработало», от разных людей. 25 % и ниже — вывод считается ложным. Подтверждение — делом: агент применил и сообщил результат.
7. Выводы-соперники (противоречащие) допускаются только для фактов и гипотез; для правил бюро — один ответ. Противоречия уходят на модерацию.
8. Срок годности по версии: при смене версии ПО — пометка «проверить», показатель не сбрасывается.
9. Подсматривание: агент запрашивает базу по ходу задачи, не только в начале.
10. Ядра на старте: **Проектирование · BIM и Revit · Процессы бюро · Инструменты (плагины, навыки, MCP)**. Запись обязательно в ядре, проект — при необходимости. Список проектов — из Schema Teams по API.
11. Отдельной «страницы входа» нет — подтверждённые выводы ядра выгружаются в справку Schema Teams.
12. Реестры проверок альбомов — источник кандидатов «типовая ошибка» (повтор замечания ≥ 3).
13. Очередь модерации с приоритетом: противоречия → записи, которые запрашивали агенты → остальные. У записи — счётчик запросов.
14. Вход без агента — веб-форма записи. Telegram и локальные модели — потом.
15. С первой версии копится массив данных для дообучения локальных моделей: записи, вердикты модератора, отметки «сработало / не сработало», вопросы.
16. Код пишет Claude Code; репозиторий открытый; установка и обновление на сервере — по SSH из локальной сети (доступ выдаёт руководитель вне репозитория).
17. Сначала основа сервиса — и сразу на сервер; дальше сервис дописывается по ходу дела на работающем сервере. Навык «Выводы» стартует до сервера на md-файлах; формат md-записи равен формату записи сервиса, чтобы импорт был механическим.

Стек и хранение (PostgreSQL + pgvector или графовая СУБД) — на усмотрение Claude Code: разбор и рекомендация в задаче 1, утверждает руководитель.

## Как работать в этом репозитории

- **Язык.** Документация, интерфейс, сообщения пользователю, тексты коммитов и PR — на русском. Идентификаторы в коде — английские. Русская типографика в текстах: «кавычки», тире —, неразрывные пробелы перед короткими словами не обязательны.
- **Открытый репозиторий — деперсонализация.** Никогда не попадают в код, документацию, примеры, тесты и историю коммитов: имена и фамилии людей, аккаунты и почта, пароли и токены, адреса и порты сервера, локальные пути, реальные записи сотрудников, данные базы. Названия Schema, Schema Brain, Schema Teams — остаются. Секреты — только в `.env` (в `.gitignore`) и в переменных окружения на сервере; в репозитории — `.env.example` с пустыми значениями. Перед каждым пушем — проверить diff и историю.
- **Ветка на задачу, PR с описанием на русском**: что сделано, что проверено и как, что осталось. Маленькие PR лучше больших.
- **Решения** — в `docs/decisions.md` с датой. **Вопросы к руководителю** — в `docs/questions.md`; вопрос не блокирует работу: принять разумный вариант, пометить в коде и в вопросе, продолжать. Блокирует только необратимое (удаление данных, выход наружу из локальной сети, платные сервисы).
- **Испытания, сомнения, отклонения** — `docs/dev-notes/<версия>.md`, не в README и не в decisions.
- **Тесты.** Логика без сервера и без базы — с тестами, которые запускаются локально одной командой; геометрия, формулы (показатель доверия, приоритет очереди), разбор md и xlsx — обязательно с тестами до сборки Docker.
- **Версии** — SemVer, `CHANGELOG.md` на русском. Сборка — одной командой (`make` или скрипт), запуск — `docker compose up`.
- **Проверка на реальных данных.** Каждый этап заканчивается проверкой не на примерах, а на реальных записях пилота или реестрах — их даёт руководитель (деперсонализированные копии вне репозитория).

## Первые задачи — по порядку, каждая отдельным PR

**Задача 1 — скелет и разбор.** Структура репозитория; ADR `docs/adr/001-стек-и-хранение.md`: сравнить PostgreSQL + pgvector против графовой СУБД по критериям — граф связей для человека, векторный поиск, простота в Docker на одном сервере, объём 6–20 человек и тысячи записей, экспорт в md, зрелость инструментов; выбрать стек сервиса; черновик схемы данных и MCP-инструментов из `docs/data-model.md` довести до `docs/spec.md`. Результат — PR с рекомендацией; руководитель утверждает.

**Задача 2 — навык «Выводы» (шаг 0, до сервера).** `skills/vyvody/`: `SKILL.md` для Claude и вариант для ChatGPT / Codex. Навык по событию внутри сессии (обошёл ошибку, повторяет действие) и в конце сессии предлагает до десяти записей (было до трёх; решение 2026-10-22) по формату из `docs/data-model.md`, показывает автору, после «ок» пишет md-файл в папку выводов пользователя. Записи — вывод или вопрос. Пилот 3–5 дней у 5–6 человек проводит руководитель; по итогам — правка формата.

**Задача 3 — скрипт по реестрам проверок.** `tools/registry-scan/`: xlsx-реестры замечаний → кандидаты «типовая ошибка» (повтор ≥ 3, с учётом разных формулировок); вывод — md или csv для модерации. Пример реестра (деперсонализированный) — запросить у руководителя через `docs/questions.md`.

**Задача 4 — основа сервиса.** `docker compose`: база, API, MCP-сервер, веб-список (записи, очередь модерации, форма записи без агента), токены для сотрудников и агентов, импорт md-записей шага 0, выгрузка датасета (JSONL). Локальный запуск и тесты. Инструкция установки по SSH — без адресов и имён.

**Задача 5 — на сервер и пилот.** Развёртывание (доступ — вне репозитория), переключение навыка «Выводы» с md на MCP, пилот 2 недели у 5–7 человек; разбор замечаний. Параллельно — граф связей в вебе и выгрузка в справку Schema Teams.

Дальше — `docs/plan.md`.

## Что уже есть в бюро — контекст

- **Schema Teams** — собственный сервис управления задачами бюро с MCP-расширением (репозиторий `SchemaTools/schema-teams`, приватный; пример устройства MCP-пакета без зависимостей и с тестами против живого сервера — `tools/admin-mcp`). Список объектов (проектов) — оттуда по API.
- **Справка Schema Teams** — база знаний бюро; MCP Schema Teams умеет читать и писать её страницы. Туда уходят подтверждённые выводы ядер.
- **Реестры проверок альбомов** — xlsx единого формата бюро; источник «типовых ошибок».
- **Плагины Revit (Schema.Tools) и SchemaMCP** — источник выводов о Revit; ядро «BIM и Revit».
- Сотрудники работают в Revit 2025–2026 по ГОСТ / СПДС и BIM-стандарту бюро; все размеры — в метрической системе.
